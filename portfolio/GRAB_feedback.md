# GRAB 포트폴리오 초안 피드백

* 대상: [GRAB.md](GRAB.md)
* 작성일: 2026-10-25

근거 링크, 커밋 고정, 테스트로 검증한 범위와 한계를 나눈 점은 백엔드 포트폴리오로서 수준이 높다. 아래 피드백은 "내용이 틀렸다"보다는 **읽는 사람이 어떻게 받아들일지**에 맞춰 우선순위대로 정리했다.

---

## 🔴 우선 보완

### 1. 실제로 겪은 일이 아니라 코드 해설처럼 읽힌다

초안 안내에도 "대안 표는 현재 구현을 설명하는 비교 분석"이라고 적혀 있듯이, 문서 전체가 **완성된 코드를 거꾸로 설명하는 구조**다. 면접관이 가장 먼저 물을 질문은 "이 문제를 실제로 겪었나요?"다.

- [x] 2.2에 계기를 한두 문장 넣는다. 예: "프론트 axios 인터셉터가 동시에 받은 401마다 refresh를 호출해 로그아웃되는 현상을 확인"
- [x] 기능을 **DROP 커머스라는 도메인과 연결**한다. "오픈 시각에 여러 탭을 띄워 둔 사용자들의 토큰이 한꺼번에 재발급된다"처럼 쓰면, 인증 세션 관리가 왜 이 서비스의 핵심 사례인지 설명된다.

### 2. 핵심 사례의 핵심 코드가 빠져 있다

2장의 차별점은 **10초 유예와 재사용 탐지**인데, 본문에 실린 코드는 `refresh()`와 rotate Lua뿐이다. 유예를 판정하는 로직은 `rejectMissingToken()`과 `refresh-token-reuse.lua` 안에 있는데, 링크로만 걸려 있다.

- [x] rotate Lua는 줄이고, 재사용·유예를 판정하는 코드를 본문에 넣는다.
- [x] Lua에 쓰인 `KEYS[1]`~`KEYS[4]`가 각각 무슨 키인지 주석이나 표로 한 줄씩 정리한다.

### 3. "세션은 유지하되 요청은 거부한다"는 정책의 이유가 비어 있다

지금 글만 보면 "탭 B는 결국 실패하는데 세션이 유지되는 게 무슨 이득이지?"라는 의문이 남는다. 다음 설명이 꼭 필요하다.

- [x] **쿠키는 탭끼리 공유되기 때문에** 탭 B가 원래 요청을 다시 보내면 A가 받은 새 쿠키가 그대로 실려 간다는 점
- [ ] 경쟁에서 진 요청이 받는 상태 코드와, 그 응답을 받은 프론트가 로그아웃하지 않고 재시도하도록 처리했는지

이 설명이 들어가야 2.3의 표 두 개가 제대로 납득된다.

### 4. 민감정보 로깅 주장과 코드가 어긋날 수 있다

3.4의 `AsyncEmailDispatcher`는 `message` 객체를 통째로 로그에 남긴다.

```java
log.warn("[AsyncEmailDispatcher.dispatch]메일 발송 대기열이 가득 차 발송하지 않음: {}", message);
```

`EmailMessage.toString()`이 마스킹되어 있지 않다면 **수신 주소나 인증 코드가 로그에 찍힌다**. 그러면 3.1의 "로그에서 민감정보 노출을 줄여야 했다"는 문장과 정면으로 충돌하고, 면접에서 바로 지적받을 수 있다.

- [ ] `EmailMessage.toString()` 구현을 확인한다.
- [ ] 마스킹되어 있다면 본문에 그 사실을 한 줄 적는다. 마스킹되어 있지 않다면 코드부터 수정한다.

## 🟡 표현과 구성

### 5. 단서가 너무 많아 자신감 없어 보인다

정직하게 쓴 점은 장점이지만, 사례마다 한계가 4~5개씩 달리고 "~로 표현하지 않습니다", "~측정한 결과는 아닙니다" 같은 문장이 반복되면 성과가 묻힌다.

- [ ] 사례당 한계는 **2~3개로 줄이고 "다음 단계" 형식**으로 바꾼다. 예: "Redis Cluster 도입 시 hash tag로 키 슬롯 통일"
- [ ] 4.5의 "화면 연동 배포 상태는 공개 전에 확인합니다"나 3.5의 "팀의 후속 변경" 같은 작성자용 메모는 체크리스트로 옮기거나 한 줄로 줄인다. 개인 기여와 팀 변경의 구분은 "PR #63, #71 기준" 표기만으로 충분하다.

### 6. 맨 앞에 요약이 필요하다

분량이 길어서 채용 담당자는 2장 중간에서 읽기를 멈출 가능성이 높다. 1장 바로 아래에 3줄 요약을 둔다.

> - 동시 재발급 경합 → Redis Lua 원자 교체 + 10초 유예로 다중 탭 세션 유지, 유예 이후 재사용 시 세션 폐기
> - SMTP 장애 격리 → 저장 후 발송, 전용 실행기, 대기열 상한
> - DB·외부 저장소 정합성 → 회원 행 잠금 + AFTER_COMMIT 삭제

### 7. 설계 이유에서 "왜"를 한 단계 더 쓴다

- [ ] **HMAC을 쓴 이유**: 6자리 코드는 경우의 수가 작아서 일반 해시로 저장하면 오프라인 대입으로 쉽게 역산된다. 이 이유가 있어야 HMAC 선택이 설득력을 가진다.
- [ ] **"가입 여부와 관계없이 같은 흐름"의 목적**: 계정 존재 여부 노출(user enumeration)을 막기 위한 것이라고 용어를 명시한다.
- [ ] **회원 행 잠금**: 낙관적 락 대신 비관적 락을 고른 이유를 한 줄 덧붙인다. 예: 충돌 시 재시도하는 대신 직렬화가 단순하고, 경합 빈도가 낮다.
- [x] **Access Token 즉시 무효화 미보장**: Access Token의 TTL 값을 함께 적어 "위험 노출이 최대 N분으로 제한된다"고 말할 수 있게 한다.

### 8. 숨어 있는 좋은 소재를 살린다

2.6 표의 `revokeAfterInterleavedRotationRemovesNewToken`(조회와 폐기 사이에 교체가 끼어드는 경우)은 까다로운 경합이고 깊이를 보여 주는 사례다. 지금은 테스트 이름으로만 나와 있다.

- [ ] 2.2의 문제 정의에 이 경합을 한 줄 추가해 강조한다.
