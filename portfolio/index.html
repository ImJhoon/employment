핵심 사례 01

동시 재발급과 토큰 탈취를 구분하는 Refresh Token Rotation

문제

네트워크 지연으로 재발급 응답을 받기 전에 클라이언트가 재시도하면, 서버에서 처리 중인 첫 요청과 같은 Refresh Token을 사용하는 요청이 겹칠 수 있습니다. 이런 중복 요청에서도 토큰 교체는 한 번만 성공해야 합니다. 또한 첫 요청이 교체를 마친 뒤 재시도가 도착하면 이미 사용된 토큰의 재사용으로 보입니다. 이를 모두 탈취로 판단해 세션을 폐기하면 정상 사용자도 로그아웃될 수 있습니다.

해결

  • 원자적 교체: 옛 토큰 삭제, 새 토큰 저장, 사용 기록 저장을 Lua 스크립트 하나로 묶었습니다. DEL이 성공한 요청 하나만 교체하므로 분산 락 없이 같은 Refresh Token의 중복 교체를 막았습니다.
  • 유예 시간 10초: 교체된 토큰이 10초 안에 오면 정상적인 중복 요청 가능성을 고려해 요청만 거부합니다. 그 뒤에 오면 탈취로 보고 세션의 현재 토큰까지 같은 스크립트 안에서 폐기합니다. 시각은 Redis TIME으로 계산해 서버 간 시계 차이를 없앴습니다.
  • 장애와 인증 실패 구분: Redis 오류는 401이 아니라 500으로 응답하고 쿠키를 지우지 않습니다. Redis 장애 한 번에 전체 사용자가 로그아웃되지 않게 하려는 선택입니다.

결과

실제 Redis 통합 테스트에서 같은 토큰으로 동시 교체 20건 중 1건만 성공했고, 유예 시간 안팎의 재사용과 판정 직전에 끼어든 교체까지 검증했습니다.

핵심 사례 02

수많은 로그인 요청에 멈추던 서버를 Argon2 동시 실행 제한으로 안정화

문제

DROP 오픈 직전에 로그인이 몰리는 상황을 k6로 재현했습니다. 운영보다 약한 t3.micro 기준(메모리 1GiB, CPU 2개, 힙 550MiB)에서 로그인 80명이 동시에 몰리자 p95가 26.1초까지 늘고 29건이 실패했습니다. 힙 OOM으로 Tomcat 스레드가 죽어, 재시작 전까지 서버가 응답하지 않은 적도 있었습니다.

원인

  • 비밀번호 해시 Argon2id(메모리 19MiB, OWASP 최소 권장값)는 해시 1건이 진행되는 동안 힙 약 19MiB를 붙잡습니다. BouncyCastle 바이트코드로 확인했습니다.
  • GC 로그로 Full GC 직후 힙을 보니, 동시 해시가 약 25건을 넘으면 힙 한도에 닿아 Full GC가 반복되고 요청이 실패했습니다.
  • 가입 여부를 숨기려고 없는 계정도 더미 해시로 검증하므로, 틀린 비밀번호 요청도 같은 비용이 들었습니다.

해결

서버를 키우거나 Argon2 메모리를 낮추는(보안 기준 위반) 대신, PasswordEncoder를 감싸 해시를 동시에 4건까지만 실행하게 했습니다.

  • 처리량은 CPU가, 힙 사용은 동시 실행 수가 정합니다. 그래서 CPU 수 근처로 묶으면 처리량은 지키면서 힙 사용만 묶을 수 있다고 판단했습니다.
  • 공정 세마포어로 먼저 온 요청부터 처리하고, 3초 안에 차례가 오지 않으면 503과 Retry-After로 거절합니다.
  • 로그인, 더미 해시, 가입, 비밀번호 변경이 모두 같은 제한을 받으므로 거절 응답으로 가입 여부가 드러나지 않습니다.

핵심 사례 03

인증 요청의 반복 ID 조회를 제거해 DB 왕복을 절반으로 줄이고 처리량 1.95배 개선

문제

JWT에는 외부 식별자인 publicId를 넣고, 서비스와 FK에는 내부 PK인 users.id를 사용합니다. 로그인 이후에도 인증 API가 내부 ID를 얻을 때마다 같은 회원을 DB에서 다시 조회했습니다. 이 반복 비용이 실제 병목인지 확인하기 위해 기준선을 먼저 측정했습니다.

원인

내 정보 조회는 ID 변환과 회원 정보 조회가 각각 별도 읽기 트랜잭션을 열었습니다. SELECT는 단순했지만 요청마다 커넥션을 두 번 빌렸고, ID 변환이 요청당 DB 왕복 약 4회 중 2회를 차지했습니다. 운영 DB와 비슷하도록 왕복 지연을 약 3ms로 설정한 환경에서는 VU 800부터 커넥션 풀이 포화되며 지연이 늘었습니다.

해결

ID 매핑 캐시와 캐시 누락 경로 개선을 함께 적용했습니다.

  • 캐시 대상과 위치: 변경되지 않는 publicId → 내부 userId 매핑만 Caffeine 로컬 메모리에 저장했습니다. 적중하면 ID 변환을 위한 DB 접근이 사라집니다. 원격 캐시의 네트워크 왕복도 추가하지 않습니다.
  • 만료와 용량: ID 대응이 바뀌지 않고 탈퇴 시 회원 행을 유지하는 정책을 전제로 TTL·무효화를 생략했습니다. 대신 최대 10만 항목으로 용량을 제한하고, 없는 회원은 저장하지 않습니다. Micrometer로 캐시 적중·누락·크기·자동 제거 횟수를 관측합니다.
  • 첫 요청 비용: ID 변환 서비스의 읽기 트랜잭션을 제거했습니다. 캐시가 비어도 자동 커밋 SELECT 한 문장으로 조회합니다. JWT에 내부 ID를 넣는 방법은 기존 Claim 계약과 충돌해 제외했습니다.
  • 회원 상태 확인: 캐시는 ID 매핑만 보관합니다. 내 정보 조회는 계속 DB에서 회원 정보를 읽고 정지·탈퇴 상태를 확인합니다.

검증

PostgreSQL 로그와 pg_stat_statements로 트랜잭션 경계·문장 수를 확인하고, netem 지연 전후 응답시간 차이로 DB 왕복 수를 추정했습니다. 캐시 적중 경로에서는 ID 변환 SELECT가 사라졌고, 누락 경로에서는 별도 BEGIN·COMMIT 없이 SELECT 한 문장만 실행됐습니다.

측정 조건

로컬 Docker에서 백엔드 2 CPU·1GiB(힙 550MiB), DB 1 CPU·512MiB, HikariCP 10개로 제한하고 netem 3ms를 적용했습니다.

동일한 테스트 계정 800개를 사용하고, 캐시 적용 전·후 서버를 번갈아 실행해 각각 두 차례 성능을 측정했습니다.

동시 가상 사용자 수를 25명부터 1,600명까지 늘리며 각 단계에서 60초간 측정했습니다. 각 사용자는 응답을 받은 뒤 1초 대기하고 다음 요청을 보냈습니다.

VU 800 초과 단계에서는 계정을 공유합니다.

표의 응답시간·처리량·획득 시간은 각 조건 2회 측정 범위입니다. 요청당 왕복·트랜잭션 수는 별도로 예열한 캐시 적중 경로의 값입니다. 개선 후 교대 측정의 캐시 누락 비율은 0.32%였고, 네 실행 모두 요청 실패·401·커넥션 타임아웃은 0건이었습니다.

  • 해석: 반복 ID 조회를 제거해 커넥션 점유와 대기를 줄였습니다. 낮은 부하에서 줄어든 중앙값 약 6.4ms도 제거한 DB 왕복 약 2회와 맞았습니다. 위 성과는 캐시 도입과 조회 트랜잭션 제거를 함께 적용한 결과입니다.

설계 회고

이번 개선은 기존 JWT의 publicId와 내부 userId를 분리한 구조를 유지하면서 반복 조회 비용을 줄였습니다. 현재 구조를 돌아보면, 자체 발급 JWT에 내부 userId를 담아 ID 변환과 매핑 캐시 자체를 없애는 대안도 검토할 필요가 있습니다. 내부 PK 비노출 정책을 조정해야 하지만, 서비스가 사용하는 식별자와 인증 정보를 일치시켜 요청 처리와 유지보수를 단순화할 수 있습니다.

남은 과제

약 1,500건/초는 이번 범위의 최고 측정 처리량이며, 개선 후 처리량 한계는 더 높은 부하에서 확인해야 합니다.

캐시는 인스턴스마다 따로 채워지므로 재기동·첫 요청·캐시 항목 자동 제거 이후의 효과는 접속 패턴에 따라 달라집니다.

같은 키의 동시 누락은 하나로 합치지 않아 중복 DB 조회가 가능하며, 회원 행 삭제나 ID 변경 정책을 도입하면 무효화 정책도 재검토해야 합니다.

핵심 사례 01

동시 수락·취소·만료에서 매칭 중복 확정을 제어

위험

한 사용자가 매칭 제안을 수락하는 순간, 상대방이 거절하거나 대기를 취소할 수 있습니다. 응답 기한인 180초(3분)가 끝날 무렵에는 수락과 서버의 만료 처리가 겹칠 수도 있습니다. 각 작업이 서로의 처리 결과를 확인하지 않고 저장하면 취소한 제안이 매칭으로 확정되거나, 같은 제안에서 매칭이 두 번 만들어질 수 있습니다. 또한 같은 요청이 포함된 두 제안이 동시에 확정되면 한 사람이 두 매칭에 묶일 위험이 있습니다. 실제로 겪은 장애가 아니라, 설계 단계에서 예상하고 대비한 상황입니다.

설계

  • 잠금 순서 통일: 모든 확정 경로가 제안 행을 먼저 잠그고, 두 요청 행을 ID 오름차순으로 PESSIMISTIC_WRITE 잠급니다. 요청에서 출발하는 대기 취소도 제안 경로로 넘겨 같은 순서를 따릅니다. 잠근 뒤에는 엔티티를 다시 읽어 최신 상태로 판정합니다.
  • 한 트랜잭션과 DB 제약: 양쪽이 수락하면 매칭, 참여자 2명, 채팅방을 한 트랜잭션에서 만듭니다. 매칭 테이블에는 요청 쌍과 각 요청에 UNIQUE 제약을 두었습니다.
  • 충돌 응답과 화면 복구: 같은 결정을 다시 보내면 기존 결과를 돌려줍니다. 이미 종료·만료된 제안이거나 잠금·제약 충돌이 나면 409로 응답하고, 화면은 현재 제안을 닫은 뒤 요청·제안·최근 결과를 다시 조회해 서버 상태에 맞춥니다.

핵심 사례 02

DB를 기준으로 Valkey 대기 상태를 보정

문제와 제약

DB에 요청이 저장되어도 Valkey 등록이 누락되거나, DB에서 매칭이 확정되어도 대기 키 삭제가 실패할 수 있습니다. PostgreSQL 트랜잭션만으로 Valkey 쓰기까지 함께 커밋할 수 없으므로, 어느 상태를 기준으로 복구할지와 실패 시 처리 순서를 정해야 합니다.

선택 이유 (사후 비교 분석)

요청·제안·매칭은 채팅방과 후기가 참조하는 기록이며, 사례 ①의 행 잠금과 트랜잭션으로 상태 전이를 보호합니다. 반면 Valkey 대기 키는 TTL로 사라지는 것을 전제로 둔 값입니다. 그래서 두 저장소가 어긋나면 PostgreSQL을 기준으로 Valkey를 맞춥니다. 잠시 어긋날 수 있다는 비용은 남기고, 보정 작업으로 그 시간을 줄이는 구조입니다.

설계와 구현

  • 역할 분리: PostgreSQL은 요청·제안·매칭을 보존하고, Valkey는 사용자별 중복 진입 방지와 TTL 5분의 대기 상태를 맡습니다.
  • 최초 등록과 롤백 보상: SET NX와 예약 토큰으로 사용자 키를 선점한 뒤 DB에 요청을 저장하고, DB 커밋 전에 Lua로 대기 키와 위치 등록을 함께 활성화합니다. DB가 롤백되면 요청 ID가 일치하는 키만 정리하고, 예약 해제도 토큰이 같을 때만 수행해 다른 요청의 키를 지우지 않습니다.
  • 커밋 후 반영: 제안 생성·확정·취소·대기 복귀에 따른 Valkey 갱신과 매칭 결과 WebSocket 알림은 DB 커밋 뒤에 수행합니다. 이 단계에서 Valkey 반영이 실패해도 이미 커밋된 DB 상태는 되돌리지 않습니다.
  • 대기 요청 보정: 5초 간격의 작업이 DB의 WAITING 요청을 100건씩 순회합니다. 요청마다 별도 트랜잭션에서 행을 잠근 뒤 아래 표에 따라 처리합니다.

검증과 결과 (2026-11-05, 프로젝트 종료 후)

개인 저장소의 ee7d2ba에서 실제 PostgreSQL·Valkey를 사용해 대기 정보 삭제, TTL 만료, 컨테이너 중단·재시작과 반복 보정을 검증했습니다. 테스트마다 대기 요청 205건과 비대기 상태의 비교 요청 4건을 새로 만들었습니다.

누락 정보 복구와 만료 처리는 100 → 100 → 5건의 배치로 전체 요청을 순회했습니다. 장애 중에는 205건의 DB 상태·수정 시각을 유지하고, 재시작 후 남은 대기 시간이 있는 102건을 복구하고 시간이 지난 103건을 만료 처리했습니다. 별도 반복 보정 실험에서는 전체 205건을 최초 복구한 뒤 배치를 9회 더 호출해, 전체 요청을 3차례 더 순회해도 신규 보정 0건과 기존 만료 시각·DB 수정 시각이 유지됨을 확인했습니다.

검증 조건과 범위: Windows의 로컬 Docker 환경(PostgreSQL 17.10·Valkey 8.1.9), 명령 타임아웃 200ms에서 실행했습니다. 스케줄러 초기 지연을 1시간으로 설정하고 보정 메서드를 직접 호출했습니다. DB 대기 시간 경과는 기록 시각을 301초 이전으로 설정하고 Valkey 키는 실제 2초 TTL로 만료시켰습니다. 검증 버전에는 Redis 명령 타임아웃 설정을 Lettuce에 반영한 수정이 포함됩니다. 각 복구 시나리오는 1회 측정한 결과로, 운영 환경의 복구 시간이나 WebSocket 알림 전달까지 보장하지 않습니다.

최신 검증 근거: 측정 보고서, 실제 Valkey 복구 테스트, 실행 스크립트

한계와 다음 단계

두 저장소를 함께 커밋하지 않으므로 일시적인 불일치는 남고, 순회량과 장애 지속 시간에 따라 복구가 5초보다 늦어질 수 있습니다. 보정 대상은 WAITING 요청의 누락된 키입니다. 종료된 요청의 잔여 키는 TTL과 만료된 위치 등록 정리에 맡기며, WebSocket 알림 유실은 보정 범위에 포함되지 않습니다.

(양방향 조건 필터, 본인 구현 시점의 후보 선정, PR #55, 후속 팀 변경 #74)
  • 후기 작성 정책과 다시한끼 지수: 완료된 매칭의 활성 참여자만 종료 후 7일 안에 상대에게 후기를 작성할 수 있게 했습니다. 사전 중복 조회와 DB UNIQUE 제약을 함께 사용하고, 저장 시 제약 충돌을 중복 후기 응답으로 변환합니다. 지수는 (2.5 + 확실히 다시 + 0.5 × 아마도 다시) / (5 + 유효 후기 수) × 100으로 계산하며 산식 버전을 관리합니다. 수식상 가상 후기 5건을 반영해 소수 후기의 점수 영향을 완화합니다. (후기 작성, 지수 산식, PR #61)
