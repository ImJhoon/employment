# GRAB 포트폴리오 면접 준비 학습 가이드

## 학습 목표와 시작점

요청 한 건이 어떻게 처리되는지 이해하고, 그 위에 포트폴리오의 세 가지 개선 사례를 연결한다. Nginx, 회원 ID 변환, 부하 테스트의 관계를 먼저 정리하면 각 사례의 필요성과 검증 결과를 설명하기 쉬워진다.

- 대상 포트폴리오: [GRAB ver2](portfolio-short.md)
- 시스템 구성 참고: [GRAB 시스템 아키텍처](architecture.md)
- 첫 학습 주제: `/api/v1/users/me` 한 요청의 전체 흐름
- 첫 번째 목표: 그림 없이 요청 흐름을 2분 안에 설명하기

개념을 하나 공부할 때마다 프로젝트의 실제 코드와 연결한다. 설명할 수 없는 용어나 수치는 별도로 표시하고, 근거를 확인한 뒤 자신의 말로 정리한다.

## 1. 포트폴리오 학습 순서

### 1단계: 전체 요청 흐름 이해하기

`/api/v1/users/me` 요청 하나를 기준으로 다음 과정을 코드에서 따라간다.

`브라우저 → Nginx → JWT 필터 → 컨트롤러 → ID 변환 → 회원 조회 → 응답`

각 단계에서 실행되는 프로그램, 호출되는 코드, 접근하는 저장소를 구분한다. 캐시 적중과 누락에 따라 흐름이 어떻게 달라지는지도 확인한다.

**설명할 수 있어야 할 질문**

- Nginx와 Spring Boot는 각각 어떤 프로그램이고 어디서 실행되는가?
- HTTPS 처리는 어디서 끝나며, Nginx와 백엔드는 어떻게 통신하는가?
- JWT 검증과 회원 ID 변환은 무엇이 다른가?
- 컨트롤러와 서비스는 각각 어떤 처리를 하는가?
- Caffeine, Redis, PostgreSQL에는 각각 무엇이 저장되는가?
- 요청 처리 중 트랜잭션이 시작되고 끝나는 위치는 어디인가?

**학습 방법과 완료 기준**

- 실제 요청 경로를 따라 관련 클래스와 메서드를 차례대로 읽는다.
- 각 단계 옆에 입력, 출력, 저장소 접근 여부를 적는다.
- 코드와 그림을 보지 않고 전체 흐름을 2분 안에 설명한다.

필터 구조를 공부할 때는 [Spring Security 공식 아키텍처 문서](https://docs.spring.io/spring-security/reference/servlet/architecture.html)를 프로젝트 코드와 함께 참고한다.

### 2단계: 회원 ID 캐시 사례 공부하기

코드 변화가 비교적 작고, DB 접근 비용과 측정 결과를 연결하기 좋아 첫 번째로 깊게 공부할 사례다.

**먼저 익힐 개념**

- 외부 식별자 UUID와 내부 숫자 PK
- SELECT, 트랜잭션, 자동 커밋, DB 커넥션 풀
- 캐시 적중과 누락, 용량 제한, TTL, 무효화
- 응답시간, 처리량, 동시 가상 사용자 수(VU)

**설명할 수 있어야 할 질문**

- 외부에는 UUID를, 내부에는 숫자 PK를 사용하는 이유는 무엇인가?
- 단순한 SELECT가 왜 병목이 되었는가?
- 트랜잭션과 DB 커넥션은 어떤 관계인가?
- 캐시 적중과 누락 시 처리 과정은 어떻게 다른가?
- 캐시 도입과 조회 트랜잭션 제거는 각각 어떤 비용을 줄였는가?
- TTL을 생략할 수 있었던 전제는 무엇인가?
- 회원 상태나 권한까지 캐싱하면 어떤 문제가 생길 수 있는가?
- `/users/me`를 측정 대상으로 고른 이유는 무엇인가?
- VU와 초당 요청 수는 어떻게 다르며, 응답 후 1초 대기는 결과에 어떤 영향을 주는가?
- `/users/me`의 측정 결과를 어디까지 일반화할 수 있는가?

**학습 방법과 완료 기준**

- 개선 전후 코드를 나란히 놓고 사라진 DB 작업을 직접 표시한다.
- 캐시 적중과 누락을 각각 하나의 요청 흐름으로 설명한다.
- SQL 문장 수, SELECT 수, 트랜잭션 수, 추정 DB 왕복 수를 구분한다.
- 처리량 약 1.95배는 정해진 로컬 조건에서 내 정보 조회 API를 측정한 결과라는 범위를 설명한다.

### 3단계: Refresh Token Rotation 공부하기

동시 요청이 공유 상태를 변경할 때의 문제와 인증 정책을 연결해서 공부한다.

**먼저 익힐 개념**

- Access Token과 Refresh Token의 역할
- 경쟁 상태와 원자성
- Redis TTL과 Lua 스크립트
- 쿠키를 공유하는 브라우저 탭과 요청 재시도

**설명할 수 있어야 할 질문**

- 두 요청이 같은 Refresh Token을 동시에 사용하면 어떤 문제가 생기는가?
- 조회, 삭제, 저장을 개별 명령으로 실행하면 왜 위험한가?
- Lua 스크립트가 원자적으로 실행된다는 것은 무엇인가?
- 10초 유예 중에는 무엇을 허용하고 무엇을 거부하는가?
- 유예가 끝난 뒤 이전 토큰이 재사용되면 무엇을 폐기하는가?
- Redis 시각을 사용하는 이유는 무엇인가?
- Redis 장애와 잘못된 토큰을 왜 구분하는가?

**학습 방법과 완료 기준**

- 요청 A와 B의 실행 순서를 직접 적는다.
- 첫 교체, 동시 재발급, 유예 중 재사용, 유예 이후 재사용을 나누어 설명한다.
- 정상 흐름뿐 아니라 요청이 서로 끼어드는 순서에서도 결과를 설명한다.
- 서버의 응답 이후 프론트엔드가 어떤 요청을 재시도하는지 확인한다.

Redis가 보장하는 스크립트 실행 범위는 [Redis Lua 공식 문서](https://redis.io/docs/latest/develop/programmability/eval-intro/)에서 확인한다.

### 4단계: Argon2 동시 실행 제한 공부하기

CPU, 메모리, GC, 동시성 제어, 부하 테스트를 함께 이해해야 하는 사례이므로 앞의 두 개선 사례를 정리한 뒤 깊게 공부한다.

**먼저 익힐 개념**

- 비밀번호 해시와 일반 암호화의 차이
- 메모리를 사용하는 해시와 동시 실행 수
- JVM 힙, 살아 있는 객체, GC, OOM
- 세마포어, 대기 시간 제한, 과부하 시 요청 거절

**설명할 수 있어야 할 질문**

- 비밀번호를 복호화 가능한 형태로 저장하지 않는 이유는 무엇인가?
- 메모리를 사용하는 해시를 동시에 실행하면 왜 문제가 되는가?
- GC가 실행되어도 처리 중인 객체를 회수하지 못하는 이유는 무엇인가?
- 세마포어는 실행 중인 요청과 기다리는 요청을 어떻게 관리하는가?
- 동시 실행 수를 4로 정한 근거는 무엇인가?
- 동시 실행 제한, 대기, 시간 초과 거절은 각각 어떻게 다른가?
- 없는 계정에 더미 해시를 수행하는 이유와 비용은 무엇인가?
- p95 감소에 거절 응답이 어떤 영향을 주었는가?
- 동시 해시 약 25건이라는 관찰값은 어떤 환경에 한정되는가?

**학습 방법과 완료 기준**

- 요청이 도착해 해시를 실행하거나 대기·거절되는 과정을 설명한다.
- CPU 부족, 힙 부족, GC 반복, 커넥션 대기를 서로 다른 현상으로 구분한다.
- 응답시간과 함께 성공 수, 서버 오류, 의도한 거절을 확인한다.
- 거절이 없는 부하 단계의 결과도 활용해 개선을 설명한다.
- 선택한 동시 실행 수에 대해 실제로 비교·측정한 범위와 추가 검증이 필요한 범위를 구분한다.

### 5단계: 나머지 담당 범위로 확장하기

핵심 세 사례를 설명할 수 있게 된 뒤 다음 순서로 학습 범위를 넓힌다.

1. 이메일 인증: 인증 코드 검증, 시도 횟수 제한, 동시 요청, SMTP 실패 처리
2. OIDC 로그인: OAuth 2.0과 OIDC의 역할, state, nonce, PKCE, 제공자 식별자
3. 프로필 이미지 정합성: DB 트랜잭션과 외부 저장소, 커밋 이후 삭제, 롤백과 실패 후 남는 상태

각 기능을 구현했다는 설명에 더해, 실패하거나 동시에 실행될 때 어떤 상태가 남는지 설명한다.

## 2. CS 학습 순서

이번 포트폴리오에서는 다음 순서로 기초 개념을 익히고 프로젝트 코드에 연결하는 것을 추천한다.

| 순서 | 학습 분야 | 먼저 이해할 내용 | 프로젝트 연결 |
| --- | --- | --- | --- |
| 1 | 네트워크·웹 | IP·포트, TCP, HTTP, HTTPS/TLS, 쿠키 | Nginx와 브라우저의 요청 흐름 |
| 2 | 데이터베이스 | SQL, PK·FK, 인덱스, 트랜잭션, 커밋·롤백, 커넥션 풀 | ID 조회와 DB 왕복 감소 |
| 3 | 운영체제·동시성 | 프로세스·스레드, 메모리, 경쟁 상태, 뮤텍스·세마포어, 교착 상태 | 동시 재발급과 해시 실행 제한 |
| 4 | Java·JVM | 객체와 참조, 힙·스택, GC, 예외, 컬렉션, 스레드 안전성 | Argon2·GC·Caffeine |
| 5 | Spring·JPA | 요청 처리, DI, 필터, 프록시, @Transactional, 영속성 컨텍스트 | 실제 코드의 실행 경계 |
| 6 | 인증·캐시 | 해시·암호화·서명, JWT, CSRF·CORS, TTL, 캐시 무효화 | 인증 정책과 Redis·Caffeine |
| 7 | 성능 측정·분산 시스템 | 처리량, 평균·p95·p99, 병목, 부하 모델, 여러 인스턴스의 상태 공유 | 성능 개선 결과와 한계 |

DB에서는 트랜잭션 기본을 익힌 뒤 격리 수준과 잠금으로 확장한다. 격리 수준의 이름을 외우는 것에 그치지 않고, 동시에 읽고 수정할 때 어떤 결과가 가능한지 이해한다. [PostgreSQL 트랜잭션 격리 공식 문서](https://www.postgresql.org/docs/current/transaction-iso.html)를 참고한다.

자료구조는 병행한다. 배열, 리스트, 해시 테이블, 스택, 큐와 시간 복잡도부터 익히고, HashMap과 캐시의 차이를 연결해 본다.

## 3. 공부한 내용을 면접 답변으로 정리하는 방법

각 사례를 공부한 뒤 다음 다섯 질문에 자신의 말로 답한다.

1. 어떤 문제였는가?
2. 원인을 어떻게 확인했는가?
3. 왜 이 방법을 선택했는가?
4. 무엇으로 검증했는가?
5. 어떤 조건에서는 효과가 줄거나 문제가 생기는가?

실제 개발 중 경험한 일, 부하 테스트에서 재현한 문제, 코드로 확인한 동작, 사후에 정리한 대안 비교를 구분한다. 확인하지 못한 부분은 추가 확인이 필요하다고 답한다.

## 4. 가장 먼저 진행할 학습 체크리스트

- [ ] `/users/me`의 요청·응답 흐름을 관련 클래스와 메서드까지 따라간다.
- [ ] Nginx, 백엔드, Docker, 각 저장소의 실행 위치와 역할을 구분한다.
- [ ] JWT 검증과 publicId → 내부 userId 변환의 차이를 설명한다.
- [ ] 캐시 적중·누락에 따라 수행되는 DB 작업을 각각 적는다.
- [ ] 트랜잭션과 커넥션 풀의 기본 개념을 학습한다.
- [ ] 포트폴리오의 성능 수치마다 측정 대상, 환경, 부하 조건, 한계를 적는다.
- [ ] 전체 요청 흐름을 그림 없이 2분 안에 설명한다.

이 체크리스트를 마친 뒤 회원 ID 캐시 사례, Refresh Token Rotation, Argon2 동시 실행 제한 순서로 깊이를 늘린다.
