## 2. STAR 경험

### 경험 1. 반복 ID 조회와 트랜잭션 조정

- **S — 상황:** GRAB에서 인증 토큰은 외부 publicId를, 서비스는 내부 userId를 사용했습니다. 내 정보 조회마다 ID 변환과 회원 조회가 별도 읽기 트랜잭션을 열었습니다. 로컬 DB 왕복 지연 약 3ms 조건에서 VU 800부터 커넥션 풀이 포화됐습니다.
- **T — 과제:** 반복 조회가 실제 병목인지 확인하고, 회원 상태 확인을 유지하면서 DB 접근 비용을 줄이는 것이었습니다. 인증·회원 기능과 관련 성능 개선이 개인 담당 범위입니다.
- **A — 행동:** PostgreSQL 로그와 pg_stat_statements로 문장·트랜잭션 경계를 확인했습니다. 변경되지 않는 ID 매핑만 Caffeine에 저장하고, ID 변환 서비스의 읽기 트랜잭션을 제거했습니다. 캐시 누락 시에는 자동 커밋 SELECT 한 문장으로 조회하고, 회원 정보·상태는 계속 DB에서 확인합니다. 같은 날 같은 환경에서 개선 전→후→전→후로 비교했습니다.
- **R — 결과:** VU 1600에서 처리량이 763.8~769.1건/초에서 1,490.3~1,504.1건/초로 약 1.95배 높아졌습니다. 예열된 요청의 추정 DB 왕복은 4.07회에서 2.01회로 줄었습니다. 캐시와 트랜잭션 조정을 함께 적용한 결과입니다.
- **범위:** 로컬 Docker, 백엔드 CPU 2개·메모리 1GiB, DB 연결 풀 10개, 계정 800개, DB 왕복 지연 약 3ms입니다. VU 1600은 실제 이용자 1600명이나 운영 처리량이 아닙니다. 개선 후 최대 처리 한계는 미확인입니다.
- **근거:** [고정 커밋 측정 보고서](https://github.com/prgrms-aibe-devcourse/AIBE7_FinalProject_Team3/blob/7c2e51b84c45d4d31eea2e7549907d40416fc323/Backend/k6/user-id-lookup/result.md), [개선 PR #226](https://github.com/prgrms-aibe-devcourse/AIBE7_FinalProject_Team3/pull/226). 이번 작업에서는 보고서 앞 155행을 원격 열람했고 PR 자체는 재검토하지 않았습니다.

### 경험 2. 로그인 OOM 재현과 자원 제어

- **S — 상황:** 한정 판매 시작 전 로그인이 집중되는 상황을 로컬 k6 부하 테스트로 재현했습니다. CPU 2개·메모리 1GiB·힙 550MiB에서 일제 로그인 80건의 실패가 발생했고, OOM으로 서버가 응답하지 않는 상황도 재현됐습니다.
- **T — 과제:** 비밀번호 해시 설정을 유지하면서 동시 연산으로 인한 힙 고갈을 제어하고, 과부하 요청의 대기·실패 응답을 정하는 것이었습니다.
- **A — 행동:** GC 로그와 BouncyCastle 바이트코드 분석으로 해시 한 건의 메모리 사용과 동시 실행의 영향을 확인했습니다. PasswordEncoder를 감싸 공정 세마포어로 해시 실행을 4건까지 허용했습니다. 3초 안에 실행 기회를 얻지 못하면 503과 Retry-After를 반환하도록 했습니다. 같은 제한을 로그인·더미 해시·가입·비밀번호 변경에 적용했습니다.
- **R — 결과:** 같은 조건의 일제 로그인 80건을 두 차례 재측정해 각 80건 모두 성공하고 OOM·응답 불가가 없음을 확인했습니다. 개선 전 실패는 각 29건·32건이었습니다. 별도의 지속 부하에서는 대기 한도 초과로 일부 요청을 의도적으로 거절했습니다.
- **범위:** 로컬 재현·개선 경험입니다. 운영 장애 대응이나 모든 부하에서 실패가 없는 설계로 쓰지 않습니다. p95 26.1초→3.0초는 포트폴리오와 일치하지만, 자기소개서에서는 핵심 수치를 분산시키지 않기 위해 생략했습니다.
- **근거:** [고정 커밋 개선 후 보고서](https://github.com/prgrms-aibe-devcourse/AIBE7_FinalProject_Team3/blob/7c2e51b84c45d4d31eea2e7549907d40416fc323/Backend/k6/login-burst/result-gr178.md). 이번 작업에서 앞 110행을 열람해 조건·성공 건수·의도적 거절을 확인했습니다. 기존 포트폴리오의 기능 브랜치 링크는 이번 열람에서 404가 반환되어 고정 커밋 링크를 사용합니다.

### 경험 3. DB 기준으로 Valkey 대기 정보 보정

- **S — 상황:** 마주한끼는 매칭 요청을 PostgreSQL에, 대기 정보를 Valkey에 저장했습니다. 두 저장소를 하나의 DB 트랜잭션으로 함께 커밋할 수 없어 정보 누락과 상태 불일치에 대비해야 했습니다. 실제 운영 장애 경험으로 단정하지 않습니다.
- **T — 과제:** 대기 정보가 사라지거나 저장소에 접근할 수 없을 때, 원래 대기 시간을 연장하거나 DB 요청을 잘못 종료하지 않도록 처리 기준을 정하는 것이었습니다.
- **A — 행동:** DB의 WAITING 요청을 기준으로 누락된 대기 정보를 남은 TTL로 복구하고, 대기 시간이 지났으면 만료시키는 보정을 구현했습니다. Valkey 조회 실패 시에는 DB 상태를 유지하고 다음 순회에서 재시도합니다. 보정은 100건 단위로 순회합니다. 프로젝트 종료 후 별도 검증에서는 실제 Valkey 중단·재시작, TTL 만료, 반복 보정을 확인했습니다.
- **R — 결과:** 로컬 재시작 시나리오의 대기 요청 205건 중 102건은 복구하고 103건은 만료시켜 미처리 0건을 확인했습니다. 장애 중에는 205건의 DB 상태를 유지했습니다. 반복 보정에서도 만료 시각과 DB 수정 시각이 유지됐습니다.
- **범위:** 2026-11-05 개인 저장소 검증 버전의 결과입니다. 명령 타임아웃 200ms, 스케줄러 대신 보정 메서드 직접 호출, 복구 시나리오별 1회 측정입니다. 운영 복구 시간·WebSocket 수신·다중 인스턴스는 미검증입니다. 당시 대안 비교 기록이 없어 선택 이유를 실제 검토 과정처럼 재구성하지 않습니다.
- **근거:** [고정 커밋 검증 보고서](https://github.com/ImJhoon/majuhankki/blob/ee7d2ba113e892bb92dd693223dcfc58d3acb95b/performance/%EB%A7%A4%EC%B9%AD_%EC%8B%A0%EB%A2%B0%EC%84%B1_%EA%B2%80%EC%A6%9D_%EA%B2%B0%EA%B3%BC.md). 이번 작업에서 전체 보고서를 열람했습니다. 구현·개인 기여는 통합 포트폴리오와 `majuhankki/notes.md`의 기존 조사 기록을 참고했습니다.

### 경험 4. 경쟁 요청의 중복 매칭 예방

- **S — 상황:** 두 사용자의 수락과 취소·거절·만료가 겹치거나, 같은 요청을 포함한 제안이 동시에 확정될 수 있었습니다. 설계 단계에서 예상한 위험입니다.
- **T — 과제:** 경쟁 요청이 있더라도 매칭 확정과 관련 데이터 생성이 일관되게 처리되도록 구현하는 것이었습니다.
- **A — 행동:** 확정 경로에서 제안→요청 ID 오름차순으로 비관적 잠금 순서를 통일하고, 잠금 뒤 최신 상태를 확인했습니다. 매칭·참여자·채팅방 생성을 한 트랜잭션으로 묶고 DB UNIQUE 제약을 함께 적용했습니다.
- **R — 결과:** 프로젝트 종료 후 실제 PostgreSQL 독립 트랜잭션을 경쟁시키는 6종 시나리오를 각 100회 반복한 검증 기록에서 중복 매칭·상태 불일치·데드락·타임아웃 0건이 확인됐습니다.
- **범위:** 600회는 반복 횟수입니다. 동시 접속자 수가 아니며 캐시·WebSocket은 mock입니다. 기존 메모에 AI가 테스트 작성·실행을 도운 이력이 있으므로 ‘테스트를 모두 직접 작성·실행했다’고 바꾸지 않습니다. 실제 대안 비교 경험과 협업 설득 과정을 추가하지 않습니다.
- **근거:** 경험 3과 같은 검증 보고서, [팀 구현 PR #46](https://github.com/prgrms-aibe-devcourse/AIBE7-Project2-Team04/pull/46), [#50](https://github.com/prgrms-aibe-devcourse/AIBE7-Project2-Team04/pull/50). PR은 기존 조사 기록에 근거하며 이번에 원격 재열람하지 않았습니다.

## 4. 제출 전 확인할 내용

- 실제 지원서 문항·글자 수 제한은 아직 확인되지 않았습니다. 문항이 있으면 내용과 분량을 재배치합니다.
- 지원 동기와 입사 후 포부는 공고·경험의 연결을 바탕으로 제안한 문장입니다. 본인이 실제로 관심을 느끼는 이유와 일치하는지 확인해야 합니다.
- Linux 개발, AWS·Azure, IaC의 개인 수행 범위는 이번에 새로 검증하지 않았습니다. 현재 초안에 숙련 주장으로 넣지 않았습니다.
- 협업을 보여주는 구체적인 의견 차이·조율·반영 경험은 자료가 부족합니다. 별도 협업 문항이 있으면 사용자 경험을 확인한 뒤 추가합니다.
- 이번 작업은 문서와 원격 보고서 열람입니다. 서비스 코드·테스트를 새로 실행하지 않았습니다. 보고서 기록을 바탕으로 결과를 서술했습니다.
