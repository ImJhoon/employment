# 티맥스티베로 DBaaS Backend 자기소개서 초안

저는 시스템의 동작을 로그와 측정으로 확인하고, 자원과 상태의 제약을 고려해 개선하는 백엔드 개발자입니다. Java와 Spring Boot 기반 팀 프로젝트로 한정 판매 커머스 ‘GRAB’과 실시간 식사 매칭 서비스 ‘마주한끼’를 개발하며, 각각 회원·인증과 실시간 매칭을 담당했습니다. 이 과정에서 DB 접근 비용, 동시 요청의 메모리 사용, 저장소 간 상태 불일치를 다뤘습니다. 이러한 경험을 바탕으로 데이터베이스의 구축과 운영을 관리하는 OwlDB의 Control Plane Backend 개발에 지원했습니다.

GRAB에서는 인증 요청마다 반복되는 DB 접근 비용을 분석했습니다. JWT의 외부 식별자를 내부 회원 ID로 바꾸는 조회와 실제 회원 조회가 별도 트랜잭션을 열고 있었습니다. 이 구조가 성능에 미치는 영향을 확인하기 위해 PostgreSQL 로그와 pg_stat_statements로 실행 문장과 트랜잭션 경계를 살폈습니다. DB 왕복 지연을 약 3ms로 설정한 로컬 환경에서는 부하가 증가할수록 커넥션 대기가 늘었습니다. 변경되지 않는 ID 매핑만 Caffeine에 캐싱하고, ID 변환 서비스의 읽기 트랜잭션을 제거했습니다. 회원 상태는 계속 DB에서 확인하도록 유지했습니다. 같은 환경에서 개선 전후를 각각 두 차례 교대 측정한 결과, 가상 사용자 1,600명 조건의 내 정보 조회 처리량이 초당 약 760건에서 약 1,500건으로 높아졌습니다. 이 경험을 통해 성능 개선에서는 쿼리 자체뿐 아니라 트랜잭션 경계와 커넥션 점유까지 살펴야 한다는 점을 배웠습니다.

요청이 집중될 때의 자원 사용도 점검했습니다. GRAB의 로컬 동시 로그인 테스트에서 메모리 부족으로 서버가 응답하지 않는 상황을 재현했습니다. GC 로그와 비밀번호 해시 구현을 분석해 Argon2의 동시 실행이 힙을 소진하는 원인임을 확인했습니다. 적용한 해시 설정을 유지하면서 동시 실행을 4건으로 제한하고, 3초 안에 실행 기회를 얻지 못하면 503과 Retry-After를 반환하도록 구현했습니다. CPU 2개·메모리 1GiB 환경에서 일제 로그인 80건을 두 차례 재측정해 각 회차 모두 성공하고 OOM이 발생하지 않음을 확인했습니다. 지속적인 과부하에서는 일부 요청을 거절하는 비용도 확인했습니다. 처리 가능한 자원과 대기 시간을 정하고, 처리할 수 없는 요청의 응답까지 설계하는 것이 안정성의 일부임을 배웠습니다.

마주한끼에서는 PostgreSQL과 Valkey의 상태가 어긋날 때를 고려했습니다. 두 저장소를 함께 커밋할 수 없으므로, DB에 남은 대기 요청을 기준으로 Valkey 정보를 보정하는 처리를 구현했습니다. 대기 시간이 남았으면 남은 TTL로 복구하고, 시간이 지났으면 요청을 만료시킵니다. Valkey에 접근할 수 없을 때는 DB 상태를 유지하고 다음 순회에서 재시도하도록 했습니다. 프로젝트 종료 후 로컬 검증에서는 실제 Valkey 재시작으로 대기 정보를 유실시킨 뒤 요청 205건 중 102건을 복구하고 103건을 만료시켜 미처리 0건을 확인했습니다. 이 경험은 여러 구성 요소가 함께 동작하는 시스템에서 기준 상태와 복구 규칙을 명확히 정하는 데 도움이 됐습니다.

OwlDB가 제공하는 DB 프로비저닝과 운영 관리 기능에서도 작업의 성공뿐 아니라 지연·실패 이후의 상태를 명확히 다루는 개발에 기여하고 싶습니다. 입사 후에는 DB 연동 방식과 클라우드 자원 관리 흐름을 익히고, 로그와 지표로 문제를 좁혀 개선 효과를 재현 가능한 조건에서 확인하겠습니다. 프로젝트에서 쌓은 성능 분석과 상태 보정 경험을 바탕으로, 사용자가 데이터베이스를 안정적으로 활용할 수 있는 플랫폼을 만드는 개발자로 성장하겠습니다.
